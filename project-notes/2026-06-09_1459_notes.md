## What this project is

Iterative self-play loop for **integer-answer math** with three roles:

| Role | Role in loop | Current setup |
|------|----------------|---------------|
| **Generator** | Proposes `QUESTION: ...` from prompt + example bank | Trained (was DPO; pivoting to GRPO) |
| **Solver** | Generates K solutions per question | **Frozen** Qwen3.5-9B, 8 samples/question |
| **Judge** | Grades solutions | Single-verify mode (`VERDICT: CORRECT/INCORRECT`) |

Each rollout yields a scalar **`question_reward`** per question — mix of **difficulty** D (solver pass rate) and **verifiability** V (judge confidence), with λ=0.35.

**Primary run tag:** `qwen35_question_dpo_only_8x8_vllmlora`  
**Rollout shape:** 32 questions × 8 solutions per cycle, solver frozen, generator-only training.

## What we tried: DPO on preference pairs

After each rollout, `train_question_from_rollout_rewards.py`:

1. Builds **all ordered pairs** from the same cycle where `reward(chosen) − reward(rejected) ≥ 0.05`
2. Runs **DPO** (not GRPO) for 25 steps @ lr=5e-5

- `initial_generator` pinned to `cycle_001/checkpoint-25` on resume

### DPO eval findings (offline tooling added in `6d97745`)

| Eval | Result | Interpretation |
|------|--------|----------------|
| Same-cycle 10% pair holdout | Cycle 4 eval_loss ≈ **0.06** | Looks great in-cycle |
| Cycle-5 rollout holdout (ckpts 1–4) | Only cycle 4 beats ln(2) ≈ **0.59**; cycles 2–3 ≈ **0.71** (worse than random) | **No cross-cycle generalization** |

**Conclusion:** Strong **in-cycle overfit** to noisy, redundant pairwise labels — not real learning that transfers.

### Label / signal anatomy

- ~32 questions/cycle, **one shared prompt**, ~**6–7 unique reward values**
- ~300–370 DPO pairs/cycle (dense all-pairs on same rollout)
- Reward ≈ **0.97 correlated with difficulty D**, not verifiability V
- D = solver pass rate on 8 samples (coarse); V = mean judge confidence
- Fixed solver → labels measure “good for this one solver,” not ecosystem improvement

### DPO eval bug we fixed

PEFT checkpoints save **policy LoRA only**, not frozen `ref`. Fresh `DPOTrainer` re-clones ref from policy → eval_loss stuck at ln(2) unless previous cycle ckpt is loaded into ref adapter. Fixed in `train_grpo_trl.py` + `eval_question_dpo_pairs.py`.

## Why DPO is a poor fit here

1. Dense pairwise pairs on ~6 reward buckets → memorization
2. Noisy scalar labels (8-sample solver + judge)
3. Train/eval misalignment when rollouts are stale (`skip_rollout_if_jsonl_exists`)
4. DPO loss → 0.06 is misleading; cross-cycle holdout is the honest metric

Process of elimination: **fitting a very noisy signal too strongly**, not “no learning at all.”

## Proposed direction: GRPO + pinned bank

**Idea:**

1. Pin **8 example bank** every cycle (`seed=4321`, same examples)
2. One **fixed proposer prompt** → sample **k completions** (k=8 or 32)
3. Train with **GRPO on scalar `question_reward`**, group-relative advantages within batch
4. **Fresh rollouts every cycle** (no JSONL reuse)

**Advantages over DPO:**

- Direct reward signal (no pair explosion)
- Natural GRPO grouping (same prompt, multiple samples)
- Fewer moving parts (no ref model / ref adapter headaches)

### Diversity gate thresholds (starting points)

From `scripts/measure_pinned_prompt_diversity.py`:

| Metric | “Enough for GRPO k=8” |
|--------|------------------------|
| `unique_questions / k` | ≥ 0.75 |
| `duplicate_question_rate` | ≤ 0.25 |
| `mean_pairwise_jaccard` | ≤ 0.55 |
| `reward_std` (after full scoring) | ≥ 0.05–0.08 |
| `unique_rewards` | ≥ 4 for k=8 |

**Caveat:** Text diversity can be fine while reward diversity is collapsed (same D buckets from fixed solver). Gate should report **both**.

### Known bug to fix before clean rerun

`generate_pairwise_data` may leave **`{question_bank_examples}` unfilled** in the prompt template. Old rollouts may not reflect a properly pinned bank. The diversity job uses `render_question_bank_block_from_config` correctly.

## Decision options (next steps)

| Option | Pros | Cons |
|--------|------|------|
| **A. GRPO + pinned bank + k=8 groups** | Cleanest; matches theory | Need diversity gate + implementation |
| **B. Keep DPO but sparse pairs** (cap 32–64, gap≥0.15) | Minimal code change | Still pairwise noise; ref headaches |
| **C. GRPO online reward** (`reward.mode=question`) | Fresh labels | 2× rollout compute during train |
| **D. Abandon generator train; eval solver-only** | Simpler | Doesn’t improve generator |

**Recommended sequence:**

1. Confirm **K=32 pinned diversity** results on server
2. If text diversity OK → **smoke GRPO** on one cycle JSONL (k=8, group-centered rewards)
3. Full loop: fresh rollouts + pinned bank + GRPO; gate on cycle holdout or fixed question bank eval (not DPO loss)
4. Fix `{question_bank_examples}` injection in rollouts
